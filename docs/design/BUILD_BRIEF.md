# Coppice design prototype: build rules shared by all 8 builders

You are building ONE of 8 design directions for Coppice as a clickable prototype. Your direction's own brief (palette, type, layout, icons, logo, motion) is a separate file; this file holds the rules every direction follows. When the two disagree, your direction brief wins on visual and motion decisions, and this file wins on process, routes, CSP and quality gates.

## 1. What Coppice is
A team outreach CRM for groups that turn over every year (student orgs at any school, hackathons, nonprofits, alumni boards). Officers claim a company before contacting it (one holder, expiring lock), work a follow-up queue sorted by most overdue (the workspace home), move companies across six stages, log outreach, import CSV sheets with duplicate flags, verify fact sheet items, and draft pitch emails with unsupported claims underlined. The name: coppicing cuts a tree to the stump and it regrows many stems from the same roots; the board leaves, the relationships stay. Taglines the owner likes: "Coppice. Capisce?" and "New board, same roots." Never call it BoilerPitch in the prototype. Do not use Purdue colors or branding.

## 4. Hard rules
- **Strict Content-Security-Policy in production.** `proxy.ts` sends `style-src 'self' 'nonce-…'` and a nonce-only `script-src`. So: never use React `style={{…}}` and never render a `style="…"` attribute from the server; never inject `<style>` tags or `<script>` tags yourself; no external URLs for fonts, images or scripts (everything is served from this app). Allowed: Tailwind classes, CSS in `app/globals.css` or CSS modules (keyframes, transitions, scroll-driven animations, `@starting-style`, View Transitions), the Web Animations API (`element.animate`), setting styles through the CSSOM in effects (`el.style.setProperty`, which CSP does not block), GSAP (`gsap` package, including ScrollTrigger, SplitText, Flip and other bundled plugins, used inside `useEffect`/`useLayoutEffect` with cleanup via `gsap.context` or `gsap.matchMedia`), the vanilla `motion` package functions (`animate`, `scroll`, `inView` from "motion") inside effects, `lenis` for smooth scroll on the landing only, `ogl` or plain canvas/WebGL, and SVG with presentation attributes. Do NOT use `motion/react` components (`motion.div` with `initial`/`animate`/`style` props): they render inline style attributes on the server, which the CSP blocks. Check `@number-flow/react` against the CSP note in your brief before using it.
- **Do not touch** `lib/`, `prisma/`, `proxy.ts`, `next.config.ts`, `vercel.json`, `tests/`, `app/(app)/`, `app/(auth)/`, `app/api/`, `components/`, `package.json` dependencies (the animation menu gsap, motion, lenis, @number-flow/react and ogl is already installed; adding any other dependency needs the design lead's approval, see section 7).
- **Uniqueness.** Your direction must share as little as possible with the other seven: draw your own logo, your own icon set (inline SVG React components in `app/demo/_<slug>/icons.tsx` or similar, drawn to your brief's icon style; do not install an icon library), your own illustrations, your own motion. Keep all your visual code under `app/demo/` and `app/page.tsx` (plus `app/globals.css`, `app/layout.tsx`, and `public/` for any raster or SVG files you create).
- **In-app motion budget.** Inside `/demo/...` motion must never slow work: interaction feedback 100 to 250 ms, panel and route transitions 150 to 350 ms, nothing that blocks input or delays content from appearing, no looping decoration on work screens, no scroll-jacking in the app. The landing page may be bold (scroll-driven scenes, pinned sections, canvas), but it must stay smooth (transform and opacity, no layout thrash) and readable.
- **Accessibility.** WCAG AA contrast for text (4.5:1 body, 3:1 large text and UI glyphs). Color is never the only signal (stages, overdue, claim state carry text or a glyph too). Every animation respects `prefers-reduced-motion: reduce` (content appears instantly, no parallax, no auto-playing motion). Keyboard focus visible everywhere; all controls are real buttons or links with labels.
- **Responsive.** Works at 1440, 1280 and 1024 desktop widths and at a 390 px phone width (officers use phone browsers at career fairs). No horizontal page scroll on phones except inside an intentionally scrollable board.
- **Writing style for any text you add** (owner's rules): no em dashes, no arrow characters, no "+" or "=" as shorthand, no "it's not X, it's Y" phrasing, no generic hype. Plain, specific microcopy.

## 5. Git discipline
- The repo's git identity is already configured; never change git config, never rewrite history, never force-push.
- Commit early and often: one small, coherent step per commit (for example "Add Ledger color and type tokens", "Draw Ledger icon set", "Build queue rows with claim states"). Aim for 25 to 60 commits across the whole build. Each message at most 20 words, no em dashes, no Co-Authored-By trailers, no mention of Claude, AI or any tool.
- Push only at milestones so Vercel preview builds stay within the daily limit: after the foundation (tokens, fonts, logo, icons, shell), after the landing page, after the screens, and after QA fixes. At most 6 pushes in total unless asked.

## 6. Quality gates before you report done
1. `npm run typecheck` and `npm run lint` pass with no errors.
2. `env -i PATH="$PATH" HOME="$HOME" npm run build` passes with no environment variables set (Vercel preview builds have none; the build script supplies placeholders for the real app's import-time checks, see `scripts/build-with-preview-fallbacks.sh`).
3. Production check with the real CSP: `env -i PATH="$PATH" HOME="$HOME" npx next start -p <port>` after the build, then a Playwright script (`require('playwright')`, `chromium.launch()` with no options; never run `playwright install`) that visits all 10 routes, collects every console error and every `securitypolicyviolation` event (listen with `page.on('console')` and an init script that records `document.addEventListener('securitypolicyviolation', …)`), and fails if any appear. Fix every violation.
4. Click-through in the same script: sign in, open a workspace, claim an unclaimed company, try to claim one held by someone else (see the refusal), log outreach, move a stage, open a company, run the CSV import with the sample file through mapping and duplicate choices, verify a fact, generate a draft, switch to Owner and force-release a claim, change a setting. Any error is a bug to fix.
5. Screenshots for the design lead's review, saved to `/home/user/wt/shots/<slug>/`: each of the 10 routes at 1440x900 (`<nn>-<route>-desktop.png`, full page for the landing and the board, viewport for others), the queue and the company page at 390x844 (`<nn>-<route>-mobile.png`), and a hover or claimed state of the queue. Also record the landing page scroll with Playwright `recordVideo` (scroll steadily top to bottom over about 20 seconds) and make a contact sheet with ffmpeg: `ffmpeg -y -i landing.webm -vf "fps=1,scale=480:-1,tile=5x4:padding=6:color=white" -frames:v 1 -q:v 4 landing-sheet.jpg`; also capture a 2-second recording of one in-app interaction (claim) and its contact sheet. View your own screenshots with the Read tool and fix anything broken, misaligned, clipped, unreadable or off-brief before reporting.

## 7. When you need the design lead
Your brief is meant to settle every design and motion decision in advance. If you hit a decision it does not cover and that matters visually or functionally (a new dependency, a motion idea not in the brief, a layout conflict between the brief and SCREENS.md, a contrast problem with a specified color), stop at a clean commit and end your turn with a message that starts with `QUESTION FOR DESIGN LEAD:` followed by the question, the options you see, and your recommendation. You will be resumed with an answer. Do not ask about things you can decide sensibly yourself within the brief's spirit.
